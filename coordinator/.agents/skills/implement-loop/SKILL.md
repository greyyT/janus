# Implement loop — one reviewed TODO per session

This skill owns both **per-TODO implementation/review** and the **task-wide continuation policy**. There is no separate implementation-review workflow. Read `../tasks/SKILL.md`, the `herdr-delegation` skill, and `../task-review-loop/SKILL.md` for the aggregate gate. Read the `handoff` skill only for a permitted handoff; the verified continuation authority below permits following its instructions without a separate `/skill:handoff` invocation. **One Janus session implements at most one TODO.** A completed TODO is a checkpoint, not task completion. Canonical STEP, TODO, CLOSEOUT and REVIEW records plus source evidence—not a launcher or runner state—support every transition.

## Entry: choose the loop mode and closeout policy

1. Require the user's explicit invocation for a **named Tasks task**. Before spawning, ask the user to choose:
   - **Automated loop:** after each approved TODO, Janus automatically hands off to one fresh session for the next eligible TODO or final integration review. This task-scoped grant covers only approved TODOs, the accepted closeout policy, and the task-wide review; it never overrides an owner gate.
   - **Manual loop:** after each approved TODO, Janus stops and asks the user to approve the **next exact action** (next TODO or integration review). No automatic handoff or further delegation before that approval. If he approves continuation, a fresh-session handoff is allowed for that action only. An approval for one TODO does not approve subsequent TODOs. After accepted integration findings, ask before starting each remediation TODO. The initial invocation, after mode and policy are selected, authorizes only the first eligible TODO.

   State the difference before asking; do not assume automated mode from words such as “finish the task.” Record the chosen mode, date, named task and task-wide authorization (automated) or first-TODO authorization (manual) in first STEP NOTES, without a fabricated quote. If mode or task is unclear, stop. A later explicit mode change applies prospectively at a safe boundary, never retroactively.
2. In the same first loop, ask for one **run-wide closeout policy** for all eligible TODOs: verified local commit, verified local commit plus push and PR per TODO, or explicit no-commit. Name the implementation repository and repeated consequence. No answer means stop. Write task-local `CLOSEOUT.md` with mode, policy, date, task/repository, repeated effect, owner authorization and first-STEP pointer. Future sessions verify and reuse both choices without re-asking. Record an explicitly changed choice with effective boundary; do not rewrite earlier commits.
3. A per-TODO PR policy additionally requires the user's affirmative task-wide authorization naming repository, remote, base, dedicated branch rule and permitted publication scope. Without these, do not select it. Before **each** push verify current branch, remote URLs, divergence, branch protections and exact outgoing commit range/diff for only that reviewed TODO; unexpected history, secrets, changed parameters or no-commit changes stop for a new decision. Never force-push or amend without fresh approval.
4. In a fresh session, an **automated** continuation requires a matching task-scoped grant plus verification of first-STEP authorization, `CLOSEOUT.md`, last approved STEP/TODO or accepted integration-remediation checkpoint, next action and absence of blockers. A **manual** continuation instead requires the user's affirmative approval for that exact next action, recorded in the prior checkpoint or given directly in this session; verify it against canonical state. A generic packet, checked TODO, completed agent turn or old manual approval is not authority. Neither mode extends to another task, new target, or owner-held STOP.

## Prepare the next TODO

5. Read `TASK.md`, `CURRENT_DESIGN.md`, accepted `TARGET_DESIGN.md` when needed, `PLAN.md`, `TODOs.md`, `KNOWLEDGE.md` when present, and the next eligible `STEP-<N>.md`. Resolve STOP gates, dependencies, target conflicts, unfinished earlier STEPs and ambiguous foreign edits before implementation. Create only the current STEP. Keep ticket continuity current when managed work has one.
6. In STEP record pre-step `HEAD`, exact planned implementation paths and each path's relation to `HEAD` (clean, modified, untracked, genuinely absent), owning Janus session, and chosen worker variant. Confirm no other active agent owns an overlapping file. Repository-wide dirt is allowed, but a planned file already modified or untracked requires the user to resolve it, postpone the TODO, or explicitly elect no-commit **before** worker edits. No same-file concurrent work or guessed line attribution. Before invoking the spawn helper, record the created worker pane ID and staged task-prompt path in STEP. The helper generates its agent name and returns it after the first turn; record that name when returned. On interruption, inspect the recorded pane and live agent before any replacement.
7. Janus reads this slice's accepted review effort from `PLAN.md`: `minimal` → `reviewer-minimal`, `medium` → `reviewer-medium`, `high` → `reviewer-high`. If absent or unreadable, use `reviewer-medium` and record the default. Neither worker nor reviewer chooses effort. A remediation TODO may adopt the retained integration reviewer under `../task-review-loop/SKILL.md` instead of spawning a fresh one.

## Implement, review and correct

8. Stage a unique `/tmp` prompt with a distinct Markdown result path and spawn `implementation-worker` in the target repository through `herdr-delegation`. Its first task instruction loads Tasks; it names task and STEP, canonical artifacts, relevant source, permitted edits and verification, and prohibits commits, pushes, contract changes or premature STEP/TODO completion. **Do not send the transient accepted planning map.** The worker implements and self-verifies. Read its report, source diff and actual verification, independently checking load-bearing claims and unexpected files; retain its pane for correction.
9. Spawn a fresh, independent reviewer at the selected effort, unless adopting the retained integration reviewer for remediation. The review prompt loads Tasks, supplies task, accepted target, PLAN, STEP, source/diff and verification evidence—not the worker's transcript or private reasoning. Require read-only review with explicit `APPROVE`, `REQUEST_CHANGES` or `BLOCKED`, and only actionable evidenced `P0`–`P2` findings (location, concrete failing scenario, impact and decisive evidence). Check introduced correctness, contracts, security, state, regression and materially avoidable complexity; exclude nits, speculative hardening and unrelated pre-existing issues. Record reviewer agent/pane and result path in STEP.
10. Janus verifies every material finding against source, recording accepted or rejected findings and reasons in STEP. For `BLOCKED`, supply a within-scope prerequisite and retry the same reviewer once or stop. For `REQUEST_CHANGES` with no accepted findings, give one evidence-based reconsideration; if still unresolved, stop. Send only accepted findings and evidence to the **same worker** for at most two correction submissions, each followed by narrow re-review with the **same reviewer** for resolution and regressions. An adopted integration reviewer is not sent a new role prompt. Capture unrelated discoveries as follow-up, not endless widening. Worker loss, failed correction, unresolved review or cap reached leaves STEP incomplete. Owner-consequential scope or target invalidation stops for the user.
11. Janus approves the STEP only after explicit reviewer approval (`clean`, `all-rejected` after reconsideration, or `accepted-after-fix`) **and** its own verification. Record approved artifact, exact changed surface, accepted/rejected findings, correction rounds, evidence and limitations in STEP.

## Verified closeout and publication

12. Under commit policy, attribute each complete approved file delta to this TODO: pre-step content matched `HEAD` or file was genuinely absent, and no foreign same-file edit occurred. A new file within accepted affected surfaces may be included if its whole delta was reviewed. Collision or overlap blocks staging. Stage only exact approved implementation paths; verify the staged diff equals the reviewed change with no unrelated index contents or partial hunk staging. Derive subject from target-repository convention; create one **local** commit and verify commit/tree matches approved change. Hook/signing failure leaves STEP unfinished; never bypass checks. If a commit exists but verification fails, record hash and mismatch and stop for the user; do not silently amend, reset or revert.
13. Only after verified commit, set STEP `COMPLETED`, check its matching TODO, record review and commit evidence, reread both, update ticket checkpoint/work log, and record that bookkeeping in STEP. In explicit no-commit policy, still require independent approval; record the user's choice and concise reviewed-change surface, complete STEP/TODO, reread both, and update ticket. Never retroactively commit no-commit work; recheck attribution before later overlapping commits. Tasks bookkeeping needs no extra review or self-referential commit.
14. For authorized PR policy, **after** local commit and STEP closeout, verify outgoing range again, publish only the individually reviewed commit on its authorized dedicated branch, create its PR, and verify URL and diff. Failure leaves the approved local STEP intact but blocks continuation: record remote status and a concrete retry/rollback question in STEP and ticket. Never claim publication or hand off as if it succeeded.

## Boundary: manual approval or automated handoff

15. Reread STEP, matching TODO, review evidence, commit/no-commit/PR result, ticket and next gate. Close ordinary reviewer then worker panes; leave a retained integration reviewer under task-review ownership. If a blocker or owner gate remains, stop in **both modes**, record exact checkpoint and ask one concrete decision question. Do not launder a blocked step into a handoff.
16. If more TODOs remain—or none remain and the aggregate integration gate is next—then:
   - **Automated:** when the next action is eligible, hand off to one fresh Janus session via the `handoff` skill without another routine approval request. Source and destination independently verify the task-scoped grant and current canonical state.
   - **Manual:** report the completed STEP and proposed **exact next action**, ask the user whether to continue, and stop. Only after affirmative approval, record its date and action in the checkpoint; then follow the `handoff` skill to hand off to one fresh session for that approved action. No answer means no handoff and no further work.

   In the packet, name the task and absolute implementation repository/task directory; reference first-STEP authorization, `CLOSEOUT.md`, the approved closeout or accepted remediation checkpoint, and the exact next action. Include retained reviewer identity and live status when relevant. Tell the destination to load this implement-loop skill and verify mode, recorded authorization, canonical state, and owner gates before delegation. Run the handoff from the Janus repository so the destination starts there.

   A failed handoff leaves this source alive; never spawn a second destination. A context limit is not permission to skip review or owner gates.
17. The next session runs `../task-review-loop/SKILL.md` when implementation TODOs are exhausted. Aggregate review and owner-held acceptance, not checked TODOs, determine completion. Accepted findings become bounded remediation TODOs. Automated mode may hand off after a Janus-accepted remediation checkpoint with no owner gate; manual mode asks the user before each remediation TODO. A retained reviewer may cross the session boundary only with recorded identity and live verification. If none can be verified, follow the task-review fallback; never invent approval.

## Stop conditions

Preserve exact in-progress STEP state, evidence paths, findings, rounds and next action as work changes. Stop on missing or contradictory authority, invalid attribution, unapproved external action, meaningful scope change, reviewer dispute/cap, failed publication, or an owner-held STOP. Report truthful partial progress and one owner decision question. Task completion requires a currently approved aggregate review round, every acceptance and owner gate, ticket continuity, and verified authorized publication; then stop without another handoff.
